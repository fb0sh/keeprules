# Coding Agent Lean Change Rules

本文件定义 Coding Agent 在设计与实现改动时的精简原则。

适用于所有 Coding Agent 及其创建的 Subagent。

**核心原则：只做当前任务真正需要的改动；先复用再新增；精简但不能省略关键正确性、安全与可验证性。**

所有 Agent 在整个任务生命周期内必须遵守本文件。

## 1. 决策顺序（写代码前必须执行）

在编写任何新代码或引入新抽象之前，**MUST** 按以下顺序检查，并在第一个成立的选项处停止：

1. **是否真的需要？**  
   该功能、选项、扩展点或灵活性是否被当前任务明确要求？未要求的部分应跳过，并在交付时说明。

2. **代码库中是否已有？**  
   是否存在可直接复用或稍作适配即可使用的函数、组件、模式、工具或既有实现？

3. **标准库或平台能力是否已覆盖？**  
   语言标准库、运行时或平台原生能力是否已能满足需求？

4. **已安装的依赖是否已覆盖？**  
   项目当前已引入的依赖是否已提供所需能力？

5. **只有以上均不满足时**，才编写最小必要的新代码。

**MUST NOT** 在未完成上述检查的情况下直接新增实现。

## 2. 改动范围控制

- **MUST** 将修改严格控制在完成当前任务所需的最小范围内。
- **MUST NOT** 对与当前任务无关的代码进行重构、重命名、格式化或结构调整。
- **MUST NOT** 为「以后可能用到」「更通用」「更优雅」等理由提前引入：
  - 新的抽象层、接口、工厂、配置系统
  - 未要求的扩展点或插件机制
  - 新的生产依赖
- **SHOULD** 当存在多种可行方案时，优先选择改动面最小、引入概念最少的方案。
- 发现任务范围存在歧义时，**SHOULD** 先按最小可行理解实现，并明确说明假设。

## 3. 精简的边界（禁止省略的内容）

精简的目标是去除无关复杂度，而不是削弱正确性与安全性。

以下内容 **MUST NOT** 以「保持精简」或「减少代码量」为由省略、弱化或推迟：

- 信任边界处的输入校验与输出编码
- 防止数据丢失、损坏或状态不一致的错误处理
- 安全相关逻辑（认证、授权、敏感数据处理、注入防护等）
- 用户或任务明确要求的功能、行为与约束
- 项目已有的关键工程规范与安全要求
- 对外部系统调用的基本失败处理

**MUST** 在精简与上述底线冲突时，优先保证底线。

## 4. 复用与依赖

- **MUST** 优先复用项目内已有实现，而不是重新编写功能等价的代码。
- **MUST NOT** 为少量代码而新增生产依赖。
- 新增依赖前，**MUST** 确认标准库、平台能力与现有依赖均无法合理满足需求。
- **SHOULD** 复用时遵循项目已有的使用方式与模式，避免引入不一致的新风格。

## 5. 验证与可检查性

- 涉及以下逻辑的改动，**SHOULD** 留下最小可运行的验证（单元测试、断言、脚本自检或等效手段）：
  - 分支与条件判断
  - 循环、递归或迭代处理
  - 解析、序列化或数据转换
  - 与权限、安全、资金、外部状态变更相关的逻辑
- 验证应覆盖关键路径与重要边界条件，而非追求形式上的完整覆盖。
- **MUST** 如实记录已执行的验证、未执行的验证以及原因。
- **MUST NOT** 通过删除、跳过或弱化已有测试来使改动通过。

## 6. 有意简化的标记

当采用已知存在明确上限的简化方案时（例如性能受限的算法、临时实现、范围受限的处理逻辑），**SHOULD** 在紧邻处用注释标明以下三点：

- 这是有意为之的简化
- 已知的上限或失效条件
- 建议的升级路径或触发条件

示例：

```text
# lean: 当前使用线性扫描。当数据量超过 10k 时需改为索引或缓存。
```

标记的目的是让后续维护者能快速识别技术债，而不是鼓励随意简化。

## 7. 交付时的披露

完成任务时，**SHOULD** 在交付说明中简要包含：

- 主动跳过的未要求功能或扩展
- 未进行完整验证的部分及原因
- 已知的简化点与潜在风险
- 对后续维护者可能重要的假设

## 8. 与其他规则的关系

- 本文件约束的是改动的范围与复杂度。
- 环境卫生、资源管理见 KEEPTIDY.md。
- 安全与敏感信息见 KEEPSECURED.md。
- 当本文件与安全、正确性要求冲突时，以后者为准。

## 9. 任务交付检查清单

完成改动前，必须确认：

- [ ] 已按决策顺序检查复用可能性。
- [ ] 修改范围未超出当前任务所需。
- [ ] 未引入未要求的抽象、依赖或重构。
- [ ] 未以精简为由省略关键校验、错误处理或安全逻辑。
- [ ] 非平凡逻辑已留下最小验证，或已明确说明未验证原因。
- [ ] 有意简化的地方已做标记（如适用）。
- [ ] 交付说明中已披露重要假设与未验证项（如适用）。

## 10. 规则执行与优先级

本文件使用以下规范性关键词：

- **MUST**：强制要求。
- **MUST NOT**：严格禁止。
- **SHOULD**：默认应当执行，特殊情况需有合理理由。

执行优先级：

1. 系统安全限制及更高优先级指令。
2. 用户明确授权与当前任务要求（不得覆盖安全与正确性底线）。
3. 本文件中的精简与范围约束。
4. 项目既有规范及相关工具约定。
5. Agent 自主决策。

当规则发生冲突时，优先选择安全、可逆、影响范围最小的执行方式，并报告无法自行解决的冲突。

**所有 Agent 和 Subagent 必须在完整任务生命周期中持续遵守这些约束。**
